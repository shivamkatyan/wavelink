# ADR-009 Bluetooth Support Boundaries

Status: Accepted (2026-09-06)

## Context
FR-030 Free Bluetooth where a public path makes emitter→receiver viable; FR-031 standards-first; FR-033 explicit matrix; FR-034 equivalent outcome (product device receives AND renders).

## Evidence (P0 Bluetooth matrix)
- Standard A2DP sink app-API: Android U, iOS U, Windows U, macOS U. Only Linux (BlueZ a2dp_sink + PipeWire media-sink) supports full receive+render via the OS.
- Generic LE-Audio receive for apps: U on Android/iOS/macOS; E on Linux (BlueZ experimental); Windows driver-level only.
- Custom Classic sockets: Android RFCOMM/L2CAP S; Windows RFCOMM S (L2CAP U); Linux S; iOS U for generic (MFi-scoped).

## Decision
Two-axis truth model, product-wide: (1) **Standard BT sink receive** = Linux only (full public path); (2) **Custom product-peer RFCOMM/L2CAP transport** = supported on Android/Windows-RFCOMM/Linux at low-bitrate lossy where the app itself decodes and renders to its own output/DAC (not an OS audio path; not claimed as hi-fi; per-platform throughput budget measured in B5); iOS is P/MFi-scoped, not part of the general product. All other cells expose a precise explanation + one-action fallback to free lossy Wi-Fi. Product never implies a stock phone can be an A2DP sink.

## Consequences
Honest matrix; BT is a convenience tier, not the headline path. Free policy exposes supported BT modes; unsupported cells are visible in UI + docs.
## Reversal
A future public A2DP-sink or generic LE-Audio receive API on a target OS upgrades that cell to standard-sink status.
