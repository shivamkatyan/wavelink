# ADR-001 Repository & Shared-Core Strategy

Status: Accepted (2026-09-06)

## Context
Cross-platform (Win/mac/Linux/Android/iOS) audio relay. Shared protocol/logic must be testable in Linux WSL2/Docker, memory-safe, low-latency controllable, cross-compilable to all targets, with mature ecosystem.

## Options
1. Shared memory-safe core in Rust + native shells (default candidate).
2. Fully native split with a language-neutral wire protocol (reuse per platform, duplication).
3. Shared core in C++ (memory-safety burden, ecosystem less uniform).
4. Shared core in another language (Go: fine for network, weaker low-latency audio/FFI story on mobile; C#: weak native mobile story).

## Evidence
- Rust crate ecosystem verified 2026-09-06: quinn (QUIC, rustls pure-Rust), webrtc-rs RTP/SRTP, Opus/FLAC bindings, mdns-sd, snow/ed25519, uniffi (Kotlin/Swift bindings) all MIT/Apache/BSD permissive and current.
- uniffi 0.32 (MPL-2.0, weak copyleft) is the mainstream Mozilla-maintained bridge for Kotlin/Swift.
- Cross-compile path: zigbuild/cargo-ndk/cross; iOS via aarch64-apple-ios targets + xcframework.

## Decision
Monorepo; Rust shared core (`core/`) for protocol schemas/versioning, capability negotiation, audio framing/queueing, codec adapters, encryption/session state, jitter buffering/telemetry, synthetic source/sink; native UI shells per platform (ADR-002). FFI via uniffi (Kotlin/Swift) and jni; platform capture/render/permission/route/services stay in shells.

## Consequences
- Single source of truth for protocol; one test surface in Linux. Cost: FFI boundary management; mobile build tooling: keep cross-compile steps in bootstrap/CI. Real-time path stays in Rust/native (not across FFI per P1 review).
## Reversal
If a core stage's C-interop cost outweighs Rust benefit, keep Rust for new code and wrap; if uniffi blocks a platform, fall back to jni/cbindgen.
